# seL4 Ethernet driver comparison

## Source inventory

- seL4 user libraries document the pc99 e1000 driver. The implementation is `libethdrivers/src/plat/pc99/intel.c` at `ef49a397b7044fc38b609a99a8c6265a97913b8e`. Entry points are `ethif_e82574_init` and `ethif_e82580_init`, which call `common_init`. The sibling `libpci/src/pci.c` enumerates functions with `libpci_add_fun` and records I/O configuration. ## Summit 2026 CN source availability

The abstract describes an Ethernet device similar to Intel e100. The presented slides identify the device as Intel i210 and explicitly link the public `util_libs` pc99 `intel.c` source. The inspected public revision exposes the two entry points listed above. The slides give no commit for the proof input. The public baseline is identifiable. The exact modified driver, CN annotations, device model and proof repository were not located in the talk materials or the project search, so their availability remains unverified. The slide results report safety verification for driver functions and leave full functional correctness open. [Summit abstract](https://www.sel4.org/Summit/2026/abstracts2026.html) · [Galois slides, pages 2, 8 and 20](https://sel4.systems/Summit/2026/slides/verifying-sel4.pdf)

## Architecture comparison

| Area | seL4 implementation | R5S implementation | Difference or potential defect | Correction or validation |
|---|---|---|---|---|
| PCI and BAR | e1000 `common_init` consumes the caller-mapped `bar0`. libpci enumerates BDFs. sDDF i.MX MAC has static MMIO in its system XML. | `R5sPcie`, `DirectEndpoint`, `program_bar`, and Microkit MMIO mappings. | R5S owns RK3568 root bring-up and endpoint BAR setup. Successful config reads exercise CPU-to-device traffic. | Keep validation of BAR width, size, PCI identity and readback. Treat device-to-DRAM DMA as a distinct test. |
| DMA allocation and addresses | e1000 `initialize_desc_ring` uses `dma_alloc_pin` and takes separate CPU and DMA addresses. sDDF sets ring VA/PA and transfers buffer addresses or offsets. | `PackedDma::from_verified_memory` checks separate CPU VA, PA and iATU-translated bus address. | An identity mapping assumption would give the NIC the wrong R5S address. | Keep explicit translated fields and test the first descriptor and buffer addresses. |
| Ring allocation and ownership | e1000 uses descriptor-done and per-submission cookies. sDDF `update_ring_slot`, `tx_provide`, and `tx_return` hand off READY descriptors and return buffers only after completion. | `Ring::initialize`, `send_frame`, and `PackedDma::publish` use RTL8125 OWN and EOR. | OWN can remain set if the endpoint cannot read the descriptor or write back. | Arm one TX slot in the diagnostic and retain OWN on timeout until shutdown. |
| Barriers and payload visibility | e1000 `raw_tx` fences before TDT and `complete_tx` fences after DD. sDDF publishes address and length before status and virtualisers maintain cached payloads. | Normal-NC pool, volatile descriptor fields, full-system barriers before OWN and doorbell and after status. | A cacheable alias would violate the DMA contract even if the driver barriers are correct. | Verify the pinned kernel and mapping, avoid aliases, and capture the wire payload. |
| MMIO, reset and engines | e1000 uses BAR registers, device reset and `initialize_transmit`/`initialize_receive` after ring setup. i.MX `eth_setup` programs ring bases before MAC enable. | `DeviceIo` validates widths and performs ordered volatile accesses. `mac::reset` and B51 setup precede bases, mastering and ChipCmd. | A PHY-only success can precede a failing TX engine. | Keep per-stage readbacks and run a TX-only probe. |
| Polling and IRQs | e1000 exposes `raw_poll` and `handle_irq`. sDDF has `handle_irq` and deferred IRQ ack in `notified`. | LAN polling runs in a scheduled provider PD with its interrupts masked. | No IRQ dependency in the test. An unbounded poll would obscure completion. | Keep one bounded TX ownership wait in the diagnostic. |
| Packet ownership and stack boundary | e1000 returns buffers through `i_cb` callbacks. sDDF uses free/active queues, `virt_tx` and `virt_rx` plus notifications. | LAN `LanService` owns its private DMA pool and copies validated frames into local protocol processing. WAN already uses separate PDs and queues. | LAN protocol and RX could obscure TX-only behavior. | Bypass both in the diagnostic and keep the existing normal LAN service. |
## m3OS Rust drivers

m3OS provides userspace Intel e1000, e1000e, igb and igc drivers. The igb driver covers I210/I211. Its `init.rs::IgbDevice::bring_up` is a reference for staged initialization, and its `rings.rs` handles descriptor ownership. The e1000 driver exposes a similar split between initialization, rings and packet I/O. These are m3OS references alongside the seL4 sources. [Pinned m3OS drivers at `03e0edce8b33c38f01d4e1075b446f270564e47e`](https://github.com/mikecubed/m3OS/tree/03e0edce8b33c38f01d4e1075b446f270564e47e/userspace/drivers) · [Intel igb source](https://github.com/mikecubed/m3OS/blob/03e0edce8b33c38f01d4e1075b446f270564e47e/userspace/drivers/igb/src/init.rs)

The closer match is m3OS's RTL8125B rev `05`. The project reports successful ARP and ping through VFIO on physical silicon. Its reported fixes include enabling ChipCmd after carrier, using the 16-bit queue-0 doorbell at `0x90`, and clearing the RXDV gate. R5S already follows all three patterns. The VFIO result does not exercise NanoPi's RK3568 inbound iATU or Normal-NC DMA mapping, so the one-shot capture remains the relevant board test. [m3OS validation notes](https://github.com/mikecubed/m3OS/blob/03e0edce8b33c38f01d4e1075b446f270564e47e/docs/roadmap/tasks/79-modern-nic-tasks.md) · [Realtek shared initialization](https://github.com/mikecubed/m3OS/blob/03e0edce8b33c38f01d4e1075b446f270564e47e/userspace/drivers/r8169/src/init.rs)
